# 第 41 课：从 Session 看对话和业务状态

两份状态，不要塞进同一个地方。

| 放哪 | 是什么 | 丢掉会怎样 |
|---|---|---|
| `TODOS` | 业务数据。对照数据库里的行 | 用户的待办没了 |
| `messages` | 这一轮对话。对照会话里的聊天记录 | 模型不知道刚才说过什么，**待办还在** |

运行：

```bash
PYTHONUTF8=1 python 41-多轮状态/41_状态.py
```

同一份 `messages` 里先「记一条 买牛奶」再「列出待办」，第二句的正文里有「买牛奶」。
再换一份只有系统提示的新 `messages`，再列出，正文里仍然有「买牛奶」。列表没跟着对话一起被扔掉。

---

## 1. 多轮只追加，不重写系统提示

一份对话里按顺序放：

```text
system          你写的规则，全程不变
user            用户这一句
assistant       模型的工单（含 tool_calls）
tool            你的 run_tool 返回的字符串
assistant       给人看的正文
user            用户下一句
...
```

密钥、数据库连接串、整本手册，都不进这个列表。对照：会话里不放密码，日志里不打密码。`OPENAI_API_KEY` 只留在环境变量。

换一个用户，就换一份 `messages`，也要换那个人自己的待办存储。本课只有一个全局列表，是为了把「列表还在」看清楚，不是生产里的做法。

---

## 2. 模型没有你的数据库

假模型第二轮会说「已根据工具结果回答」，是因为它 **读到了你喂回去的 tool 消息**。你要是不执行 `list_todos`、不把 `TODOS` 的内容写进那条消息，模型看不见「买牛奶」，哪怕上一句刚加过。

对照：LLM 不是事务库。提交成功的标志是你的 `append`，不是模型说「好的我记下了」。

---

## 本课肌肉记忆

1. 业务状态和对话记录分开存
2. 新对话不会自动清空待办，清空是 `reset` 或按用户删数据
3. `messages[0]` 不被工具结果改写
