# 第 42 课：从 SPI 看 MCP

你在 `chat.completions` 里传的 `tools`，已经是一份契约：名字、自然语言说明、JSON Schema。MCP（Model Context Protocol）解决的是另一件事：让 **别的进程** 来发现并调用这份契约。

运行：

```bash
PYTHONUTF8=1 python 42-MCP只看协议/42_协议.py
```

先打印两个工具名和 schema。然后 `TOOL:ECHO-TOOLS`：带了说明书时，正文里同时有 `list_todos` 和 `add_todo`；没带时，正文是 `工具清单: （没有）`。

本课不安装 MCP SDK，也不写一个常驻服务。

---

## 1. 同进程的 tools，和进程外的 MCP

| | 你现在写的 | MCP |
|---|---|---|
| 谁发现工具 | 你每次请求自己带上 `tools` | 客户端调用 `list_tools`，向另一个进程要清单 |
| 谁执行 | 同一个进程里的 `run_tool` | 另一个进程的 `call_tool`，常见传输是 stdio |
| 契约长什么样 | `name` + `description` + `parameters` | 仍是名字、说明、JSON Schema，字段名不同 |
| 本阶段要不要做 | 要 | 认得出即可 |

对照：现在是在一个 Spring 进程里直接调 Service。MCP 像把这些 Service 用 SPI 暴露给进程外的宿主（桌面客户端、IDE）。宿主负责问模型、再回头调你。循环和步数上限如果在宿主那边，你的进程就只剩「校验并执行」。上限不能因为换了协议就消失，只是换了放置的地方。

协议细节会变。会变的是 URL 和字段名，不会变的是：模型选工具，不可信的参数进你的校验，执行权在你的代码。

---

## 2. 为什么先不造框架

LangChain、各种 Agent 框架，都是在这份契约外面再包一层循环。循环你在第 40 课已经有了，而且上限看得见。框架把循环藏进库里之后，步数、超时、系统提示被谁改掉，都要再翻一层才能看见。

组里已经在用某个框架时再去认它的名词。默认架构仍是：官方 SDK + 你自己的 `run_loop`。

---

## 本课肌肉记忆

1. `tool_specs()` 是契约，不是框架
2. 没放进这次请求的工具，模型就不该点到；假模型会用 ECHO-TOOLS 证明这一点
3. MCP = 进程外发现和调用。本课不实现它
